# 028 · Navigation & Layout Robustness — Plan

## Enfoque

Se reforzará el shell existente de Next App Router sin introducir dependencias: se corregirán los destinos y enlaces, se añadirán los boundaries de error de Next, y el Sidebar se convertirá en un drawer controlado solo en móvil mediante los primitives shadcn/Radix ya disponibles. La autenticación y las llamadas de libros conservarán sus contratos actuales, pero compartirán helpers para validar destinos internos y propagar el status HTTP. Las pruebas Vitest/RTL cubrirán navegación, accesibilidad, errores, seguridad de `redirectTo`, paridad SSR/cliente e i18n antes de ejecutar test, lint y build.

## Decisiones

- **Drawer solo bajo `sm`** — Se conserva el sidebar fijo actual en `sm` y mayores para respetar el layout existente; en móvil se usa el primitive drawer/overlay de shadcn/Radix ya instalado, en lugar de añadir una librería o rediseñar la navegación.
- **`redirectTo` como ruta interna relativa** — Se valida en un helper compartido y se aplica tanto en formularios como en el callback; cualquier valor ambiguo o externo cae en `/dashboard`, descartando redirects absolutos, `//` y parámetros que puedan abrir un redirect externo.
- **Idioma SSR mediante cookie de preferencia** — `localStorage` no existe en el servidor, por lo que la cookie `bookshelf:language` será la fuente SSR cuando contenga `es` o `en`, con `es` como fallback; el contexto seguirá sincronizando la selección y `document.documentElement.lang` en el cliente. No se añade middleware ni dependencia de i18n.
- **Error HTTP tipado en frontend** — Se conserva `Error` como base para compatibilidad con React Query, añadiendo propiedades `status` y `code` derivadas de la respuesta; así 401 puede iniciar el flujo de sesión y 5xx puede llegar a `ErrorState` sin convertir todos los errores en una abstracción nueva.
- **Boundaries en la raíz de `app`** — `not-found.tsx`, `error.tsx` y `global-error.tsx` se colocan en la raíz para cubrir todo el App Router; `error.tsx` seguirá las exigencias de Next de ser client component y `global-error.tsx` será autosuficiente con su documento HTML.
- **Mantener el árbol de providers actual (Z5-09)** — `QueryClientProvider`, `ThemeProvider`, `SettingsProvider`, `SessionProvider`, header y Sidebar se mantienen porque necesitan estado, hooks o eventos; extraerlos o refactorizar el árbol a Server Components queda fuera de alcance y se documenta, no se fuerza en esta feature.

## Riesgos

- **Diferencias de APIs de drawer/foco entre shadcn/Radix y tests jsdom** — Reutilizar los componentes ya presentes, mantener fallback explícito de Escape/overlay y probar comportamiento observable (aria, visibilidad y callbacks), no detalles internos de Radix.
- **Pérdida o manipulación de `redirectTo` durante OAuth/callback** — Construir parámetros con `URL`/`URLSearchParams`, validar en cada frontera y probar `//evil.example`, esquemas, hostname, valores vacíos y rutas con query; nunca interpolar sin validar.
- **Hydration mismatch del idioma** — El layout solo usará la cookie disponible en SSR y valores normalizados; el efecto del SettingsProvider actualizará el DOM después de hidratar y las pruebas cubrirán cookie `en` y `es`.
- **Cambios en el formato de `authors` o en la consulta Supabase** — Encapsular la condición título/autor en la misma forma que el API, añadir mocks que inspeccionen ambas ramas y comparar el resultado SSR con el fetch de cliente.
- **Redirección repetida ante 401 o pérdida del contexto de ruta** — Guardar pathname y query actuales, evitar navegar si ya se está en auth y comprobar el estado antes de ejecutar el redirect; cubrir refresh, error inicial y error de paginación.
- **Regresión visual del shell y de imports** — Mantener clases/layout de escritorio, usar una comprobación de imports para `book-detail → components/settings` y finalizar obligatoriamente con test, lint y build del frontend.
